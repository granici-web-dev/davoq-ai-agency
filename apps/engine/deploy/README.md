# Развёртывание

Всё живёт на одной машине: прокси с сертификатом, API, воркер, Postgres
с pgvector и Redis. Пилоту хватает 2 ядер и 4 ГБ (Hetzner CX22, ≈4 € в месяц) —
считает Bedrock, сервер только раздаёт и хранит.

Serverless не подходит: нужен Postgres с векторным поиском, живые SSE-соединения
и очередь. Всё это состояние, а не функции.

---

## Что нужно до первой команды

1. **Сервер** с Docker и Docker Compose. Debian 12 или Ubuntu 24.04.
2. **Домен для API**, например `bot.example.ro`, и его A-запись, указывающая
   на адрес сервера. **До первого запуска**: Caddy запрашивает сертификат сразу,
   а у Let's Encrypt недельные лимиты на неудачные попытки.
3. **Ключи AWS** с политикой `infra/bedrock-policy.json`, применённой в консоли.
4. **Почтовый отправитель** на домене клиента, со SPF и DKIM.

## Установка

```bash
git clone <репозиторий> /opt/assistwidget
cd /opt/assistwidget

cp .env.prod.example .env.prod
nano .env.prod            # заполнить всё; пустые значения остановят запуск

docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

Порядок запуска задан зависимостями: база → миграции → API и воркер → прокси.
Служба `migrate` отрабатывает и завершается; API стартует только после её успеха.
Сервер, поднявшийся раньше схемы, отвечал бы 500 на всё и выглядел бы как
поломка приложения, хотя это гонка запуска.

Проверить:

```bash
docker compose -f docker-compose.prod.yml --env-file .env.prod ps
curl -s https://bot.example.ro/health          # {"ok":true}
```

### Пароли и почему их два

Приложение и миграции ходят в базу **разными ролями**, и это не формальность.
Владелец базы — superuser, а superuser обходит даже `FORCE ROW LEVEL SECURITY`:
под ним изоляция клиентов существует только на бумаге. Поэтому:

* `POSTGRES_PASSWORD` — владелец. Миграции и заведение клиентов, больше ничего.
* `APP_DB_PASSWORD` — роль `assistwidget_app`, без права обходить RLS. Под ней
  работает всё остальное.

В миграции `002` пароль роли задан как `dev` — это нормально для разработки
и никуда не годится на сервере. Правкой миграции его не сменить, она уже
применена; вместо этого `APP_DB_PASSWORD` подставляется отдельным шагом при
каждом прогоне миграций.

### `SECRETS_KEY`

```bash
openssl rand -hex 32
```

**Менять нельзя никогда.** Со сменой ключа токен Google Drive и ключи
коннекторов станут нечитаемыми, и восстановить их будет неоткуда: в резервную
копию ключ не попадает намеренно. Запишите его туда же, где остальные пароли
установки.

## Резервные копии

```bash
./scripts/backup.sh          # база и файлы клиентов в ./backups
./scripts/restore-check.sh   # учебное восстановление последней копии
```

В cron:

```cron
15 3 * * *  cd /opt/assistwidget && ./scripts/backup.sh >> backups/backup.log 2>&1
30 4 1 * *  cd /opt/assistwidget && ./scripts/restore-check.sh >> backups/restore.log 2>&1
```

Копируются оба хранилища, и оба обязательны: в базе материалы, переписки, заявки
и зашифрованные токены; в томе `uploads` — сами загруженные файлы, без которых
переиндексация невозможна.

`restore-check.sh` разворачивает копию в отдельную базу и проверяет не «прошло
без ошибок», а содержимое: есть ли клиенты, документы, фрагменты, и на месте ли
`FORCE ROW LEVEL SECURITY`. Пустая база восстанавливается без единой ошибки
и выглядит успехом — на это и рассчитана проверка.

**Копия на том же диске спасает от испорченных данных, но не от смерти диска.**
Увозите `./backups` куда-нибудь ещё — хоть `rsync` по расписанию.

## Наблюдение

Два слоя, и второй не заменяет первый.

**Наблюдатель** (`watchdog`) раз в минуту спрашивает у API `/health/ready`
и пишет письмо на `WATCHDOG_EMAIL`, когда что-то ломается. Проверяются база,
Redis, живость воркера, заторы и упавшие задания в очередях, место на диске.

Тревога поднимается после трёх неудач подряд, а не после первой: перезапуск
контейнера и секунда сетевой заминки дают единичный отказ, а письмо на каждый
такой отказ учит человека не читать эти письма.

**«Мёртвая рука»** (`HEARTBEAT_URL`) — обязательна, и вот почему. Наблюдатель
живёт на том же сервере: умерла машина, кончилась сеть, хостер выключил свет —
он умирает вместе со всем остальным, и письма не будет ни от кого. Изнутри
нельзя доложить о собственной смерти.

Поэтому пока всё хорошо, наблюдатель дёргает внешний адрес. Внешняя служба
поднимает тревогу, когда сигналы **перестают** приходить — молчание становится
сигналом. Годится любой бесплатный тариф (healthchecks.io, Better Stack,
cron-job.org) или cron на другой машине. На этом же сервере — бессмысленно.

Отдельно стоит заметить: сигнал не идёт и тогда, когда сломана только почта.
Это не побочный эффект, а свойство: канал оповещения тоже может лечь, и молчание
поймает даже этот случай.

Что проверяется:

| | Что значит поломка |
|---|---|
| база | не отвечает или недоступна схема |
| очередь | Redis не отвечает |
| воркер | молчит больше трёх минут: документы не индексируются, письма о заявках не уходят |
| задания | есть упавшие или очередь больше сотни |
| диск | меньше 10% свободно — самая тихая поломка: виджет отвечает и выглядит исправным |

Посмотреть состояние руками:

```bash
D="docker compose -f docker-compose.prod.yml --env-file .env.prod"
$D exec api node -e "fetch('http://127.0.0.1:3000/health/ready',{headers:{'x-ops-token':process.env.OPS_TOKEN}}).then(r=>r.json()).then(d=>console.log(JSON.stringify(d,null,2)))"
$D logs -f watchdog
```

`/health` (живость) и `/health/ready` (готовность) — разные вещи. По первой
docker перезапускает контейнер, поэтому она не трогает ничего внешнего:
моргнувшая база перезапустила бы исправный API и добавила к одной неполадке
вторую. Вторая наружу не отдаётся вовсе — закрыта токеном и не пропускается
прокси.

## Нагрузка: что замерено

`npm run test:load` гоняет ступени по одновременным диалогам на отдельном
временном клиенте и убирает его за собой. Каждое сообщение — настоящий вызов
модели, то есть настоящие деньги; расход печатается в конце (полный прогон
из 112 запросов — около $0.30).

Замер от 21.08.2026, аккаунт Bedrock `eu-central-1`, модель Haiku 4.5,
потолки по умолчанию:

| одновременно | ответили | отказ: наш потолок / квота модели | до первых знаков p50 / p95 | весь ответ p50 / p95 |
|---|---|---|---|---|
| 1 | 16 из 16 | 0 / 0 | 1.4 с / 2.5 с | 2.6 с / 3.8 с |
| 4 | 16 из 16 | 0 / 0 | 1.2 с / 3.9 с | 2.4 с / 5.4 с |
| 8 | 16 из 16 | 0 / 0 | 1.2 с / 4.3 с | 2.4 с / 6.4 с |
| 12 | 16 из 16 | 0 / 0 | 1.1 с / 2.3 с | 2.6 с / 5.0 с |
| 16 | 3 из 16 | 4 / 9 | 1.2 с / 3.2 с | 2.1 с / 3.8 с |
| 24 | 3 из 16 | 4 / 9 | 1.4 с / 4.1 с | 1.9 с / 5.2 с |
| 32 | 3 из 16 | 4 / 9 | 1.1 с / 4.7 с | 2.3 с / 5.9 с |

**Ошибок ноль на 112 запросов.** Всё, что не прошло, — честный 503 «занято».

Три вывода, и второй из них важнее остальных.

**Задержка не растёт под нагрузкой.** До первых знаков полторы секунды и на
одном диалоге, и на тридцати двух. Потому что лишнее отсекается сразу, а не
ставится в очередь: отсечённый запрос стоит мгновение, а поставленный в очередь
заставляет ждать всех.

**Упирается не наш потолок, а квота Bedrock.** На шестнадцати одновременных
наш потолок отсёк 4 запроса, а квота модели — 9. Поднимать
`CHAT_MAX_PER_TENANT` в этой ситуации бессмысленно: он не мешает. Если в журнале
много `reason: upstream`, действие — заявка на увеличение квоты в Service Quotas
у Amazon, а не правка конфигурации.

**Соединений с базой в пике — два.** Не двенадцать. Работа с базой разнесена
на короткие заходы до и после обращения к модели; на время самого обращения
соединения не существует.

### Чего этот замер не говорит

Он снят на машине разработчика против настоящего Bedrock. Ответ бота — это
ожидание Bedrock, а не работа нашего процесса, поэтому цифры задержки говорят
о нагрузке на аккаунт Bedrock, а не о железе. **Переносить их на Hetzner
нельзя.** Повторите замер на боевом сервере после установки: команда та же.

Не замерено: несколько клиентов одновременно (общий потолок `CHAT_MAX_CONCURRENT`
на одном клиенте никогда не достигается), длинные документы в очереди
параллельно с диалогами, поведение при часовой недоступности Bedrock.

## Обновление

```bash
cd /opt/assistwidget && git pull
docker compose -f docker-compose.prod.yml --env-file .env.prod up -d --build
```

Миграции применятся сами, до старта нового API. Перед обновлением —
`./scripts/backup.sh`, это тридцать секунд.

## Журналы

```bash
D="docker compose -f docker-compose.prod.yml --env-file .env.prod"
$D logs -f api        # запросы, ошибки модели, отброшенные по языку ответы
$D logs -f worker     # разбор документов, сверка Drive, письма
$D logs -f caddy      # сертификаты
```

Тела запросов и ответов в журнал прокси не пишутся: там вопрос посетителя
и ответ бота, а им место в базе, где они под RLS и удаляются по сроку хранения.

## Чего здесь пока нет

Честно, чтобы не обнаружилось на пилоте:

* **Замера под нагрузкой.** Потолки в `.env.prod.example` поставлены по здравому
  смыслу и проверены всплеском из четырнадцати запросов. Это не замер.
* **Второй машины.** Всё на одной: её перезагрузка — это простой. Наблюдатель
  об этом сообщит (через мёртвую руку), но починить некому и нечем.
* **Журналов дольше нескольких дней.** Docker крутит их сам; долгого хранения
  и поиска по ним нет.
