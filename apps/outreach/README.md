# outreach

Холодные email-кампании: поиск клиентов и вербовка партнёров.

Отдельный сервис, не часть движка чат-бота. Общий инстанс Postgres, своя схема
`outreach`. TypeScript, Node, кабинет на Next.js.

> **Состояние: план.** Заведены схема и этот документ. Кода нет ни строки, и
> в каталоге продуктов агент стоит как `planned`. Модули пишутся по одному,
> каждый — отдельным коммитом, в порядке ниже.

---

## Зачем он существует

Инструмент для себя: искать клиентов Davoq и вербовать партнёров. То, что он
одновременно заведён продуктом на витрине, — решение осознанное, но продавать
его можно будет не раньше, чем он отработает на нас. Обещание, за которым нет
собственного опыта, — это чужой риск за наш счёт.

---

## Четыре модуля

### 1. research — собрать и обогатить список

Вход — конфиг кампании с описанием сегмента. Выход — строки в `prospects`.

Поиск по сегменту, разбор сайта каждого кандидата (род деятельности, язык,
город, наличие чат-виджета, контакты, ЛПР), 2–4 конкретных факта в `evidence`,
проверка каждого адреса через API верификации.

`invalid` не рассылается никогда. Это закреплено ограничением в базе, а не
проверкой в коде: проверку обходит любой новый путь к постановке в очередь.

### 2. composer — написать письма и дать их утвердить

Четыре варианта первого письма разными углами захода плюс два follow-up
(день 4 и день 9). Каждое: зацепка из `evidence` этого кандидата в первом
абзаце, 60–90 слов, язык из конфига, подпись с реквизитами, строка-источник,
однокликовый отказ в футере. Ни одного обещания и ни одной цифры сверх
заданных в конфиге кампании.

Кампания сохраняется как `DRAFT`. Утверждение — экран, где видно всё сразу:
сегмент, все варианты, полный список получателей с их фактами. Кнопка
нажимается один раз на кампанию. Без неё не уходит ничего.

### 3. sender — отправка и разбор входящих

Отправка только по `APPROVED`, только с доменов из `ALLOWED_DOMAINS`,
`suppression` проверяется перед КАЖДЫМ письмом, потолок из конфига (по
умолчанию 15 писем на ящик в день), паузы кампании и глобальная — немедленные.
Каждая отправка пишется в `sends` целиком: кому, чем, из какого ящика, когда.

Входящие приходят вебхуком. Любой ответ останавливает цепочку. Классификация:
`INTERESTED` / `NOT_NOW` / `NO` / `ANGRY` / `AUTO_REPLY`. Отказ, злость и
отписка — в `suppression` навсегда. Интерес — уведомление и черновик со
слотами. «Не сейчас» — напоминание через N дней, тоже черновиком.

### 4. optimizer — раз в неделю, руками

Метрики по вариантам, перевзвешивание по принципу многорукого бандита (вес
пропорционален положительным ответам, не меньше 50 отправок на вариант до
первого пересчёта), разбор текстов ответов включая отказы, один-два новых
варианта на замену худшему — черновиком, с утверждением. Отчёт в Markdown.

Варианты не отключаются, а взвешиваются: при малых объёмах разница между ними
чаще шум, чем сигнал.

## Платформа отправки: Instantly или Smartlead

**Рекомендую Smartlead — но с оговоркой, которая важнее самой рекомендации.**

Сначала оговорка. Обе платформы меняют API и состав вебхуков чаще, чем выходят
их обзоры, и всё, что я могу сказать об их сегодняшних возможностях, — это то,
что было верно на момент моего обучения. Выбор ниже сделан по требованиям
нашей конструкции, а не по списку возможностей, и перед первой строкой
`sender` три пункта обязаны быть сверены с текущей документацией.

### Чего мы требуем от платформы

| | Зачем это нам |
|---|---|
| 1. Вебхук ответа с **полным телом письма** | Без текста нечего классифицировать. Уведомления «пришёл ответ» недостаточно: весь модуль обработки входящих построен на разборе формулировок. |
| 2. Добавление получателей с **произвольными полями** | `evidence` уезжает в письмо подстановкой. Без своих полей персонализацию пришлось бы делать на нашей стороне и слать готовый текст — это лишает платформу смысла. |
| 3. **Остановка цепочки для одного получателя** через API | «Любой ответ останавливает follow-up» — наше правило, и выполняем его мы. Если остановить можно только руками в их кабинете, правило перестаёт быть правилом. |
| 4. Ротация ящиков с **потолком на ящик** | Иначе потолок придётся считать самим и всё равно надеяться, что платформа его не превысит. |
| 5. **Подпись вебхука** | Вебхук ставит статусы и заносит адреса в suppression. Незаверенный вебхук — это открытая ручка, меняющая состояние. |
| 6. Отписки, которые можно **зеркалить к себе** | Наш suppression-list общий на все кампании и должен быть полнее платформенного, а не наоборот. |

### Почему Smartlead

Пункты 1 и 3 — решающие: на них держатся два из четырёх модулей. По моим
сведениям Smartlead исторически даёт более полный доступ к переписке на уровне
сообщений и более прямое управление отдельным получателем, тогда как Instantly
сильнее в готовом продукте для человека за экраном, а не для программы.
Instantly при этом заметно распространённее, и это не пустяк: больше готовых
ответов, когда что-то пойдёт не так.

### Как сделать выбор дешёвым

`sender` пишется на интерфейс, а не на платформу:

```ts
interface SenderPlatform {
  pushProspects(campaignId: string, rows: ProspectPayload[]): Promise<void>;
  send(send: PlannedSend): Promise<{ providerMessageId: string }>;
  stopSequence(campaignId: string, email: string): Promise<void>;
  verifyWebhook(raw: string, signature: string): WebhookCheck;
  parseEvent(event: unknown): InboundEvent | null;
}
```

Одна реализация сейчас, вторая — если первая разочарует. Так решение о
платформе перестаёт быть решением на годы: цена ошибки — один адаптер.

**Сверить до начала работы над `sender`:** есть ли в вебхуке полное тело
ответа; есть ли остановка цепочки для одного получателя; чем подписывается
вебхук.

## Конфиг кампании

### lead_gen — поиск клиентов

```yaml
name: "Producători de mobilă, RO, 5-50"
type: lead_gen
language: ro
segment: "producători de mobilă la comandă, România, 5-50 angajați"
sources:
  - "listă-firme.ro"
  - "google:producători mobilă la comandă {oraș}"
rate_limit_per_mailbox_per_day: 15
follow_up_days: [4, 9]
not_now_remind_days: 45
sender:
  name: "Serghei Granici"
  title: "Davoq"
  signature: "Davoq · davoq.md"
claims:                     # всё, о чём письмам разрешено говорить
  - "widget de chat pe site care răspunde noaptea"
  - "pilot la un producător de mobilă"
cta: demo
```

### partner_recruiting — вербовка партнёров

```yaml
name: "Designeri de interior pentru brandul X"
type: partner_recruiting
language: ro
segment: "designeri de interior, România, proiecte rezidențiale"
sources:
  - "houzz.com"
  - "archello.com"
  - "instagram:public"      # только открытые профили
segment_levels: [premium, mid]
rate_limit_per_mailbox_per_day: 15
follow_up_days: [4, 9]
partnership:
  commission_range: "10-15%"
  terms: "comision la proiectele aduse, plata la livrare"
materials:                  # уходят автоматически после AGREED
  - "parteneriat-x.pdf"
crm_webhook: "https://…/hooks/partners"
cta: call
```

Всё, что письму разрешено обещать, стоит в конфиге. Деталей денег сверх
`commission_range` в письмах нет: их обсуждает владелец кампании лично.

## Чего сервис не делает

- не отправляет ничего без утверждения кампании;
- не заменяет варианты писем без утверждения;
- не парсит LinkedIn и закрытые платформы;
- не отправляет с доменов вне `ALLOWED_DOMAINS`, и `davoq.ai` запрещён
  отдельно и жёстко — репутация основного домена дороже любой кампании;
- не пишет в журнал ничего сверх нужного: адрес, имя, компания — да,
  остальное — нет.

## Чек-лист запуска кампании

1. Конфиг кампании: сегмент, источники, язык, что письмам разрешено обещать.
2. `research` — прогон и глазами по списку: те ли это компании.
3. Проверка адресов прошла, `invalid` отсеяны.
4. `composer` — четыре первых письма и два follow-up прочитаны целиком.
5. Список получателей прочитан: у каждого есть факт, на который ссылается
   письмо.
6. Ящики заведены, домены в `ALLOWED_DOMAINS`, прогреты.
7. Suppression пополнен доменами действующих клиентов.
8. **Approve.** С этого момента письма уходят.
9. Через неделю — `optimizer`, отчёт прочитан, новые варианты утверждены
   или отклонены.
